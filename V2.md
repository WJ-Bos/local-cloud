# V2 Feature Planning — Extended Database Configuration

> Incremental additions to give users more control when provisioning a database.
> Each feature is self-contained and can be implemented independently.

---

## Feature 1 — Version Picker

### What it is
Allow the user to choose a specific version of the database engine when creating an instance,
instead of always getting a hardcoded default.

### Why it matters
Different projects target different engine versions. A user might need Postgres 14 for an older
app, or want to test against the latest Postgres 16. This is one of the first things real managed
database services (RDS, Cloud SQL) ask you to choose.

### How it works
The Docker image tag is the version. The terraform config currently hardcodes tags like
`postgres:15-alpine` and `mysql:8.0`. This feature replaces those hardcoded strings with a
user-supplied version that gets templated into the image field.

**Terraform change (example for PostgreSQL):**
```hcl
# Before
image = "postgres:15-alpine"

# After (version = "16")
image = "postgres:16"
```

### Supported versions per type (proposed defaults)
| Engine     | Available versions          | Default |
|------------|-----------------------------|---------|
| PostgreSQL | 13, 14, 15, 16              | 15      |
| MySQL      | 5.7, 8.0, 8.4               | 8.0     |
| MariaDB    | 10.6, 10.11, 11.1           | 11.1    |
| MongoDB    | 5.0, 6.0, 7.0               | 7.0     |
| Redis      | 6.2, 7.0, 7.2               | 7.2     |

### Changes required
- **Database schema** — add `version VARCHAR(20)` column to `databases` table
- **`CreateDataBaseRequestDto`** — add optional `version` field with validation (must be in allowed list per type)
- **`DatabaseConfigProvider`** — replace hardcoded image tags with the passed-in version string
- **`TerraformService.provisionDatabase`** — pass version through to config provider
- **`DatabaseProvisionService`** — read version from request, pass to terraform
- **`DatabaseResponseDto`** — include `version` in the response so the UI can display it
- **Frontend `DatabaseForm`** — add a version dropdown that re-populates when the DB type changes

## Feature 2 — Persistence Toggle

### What it is
Allow the user to opt into data persistence for their database container. When enabled, a named
Docker volume is created and mounted into the container so that data survives container restarts
and recreations. When disabled (the current behaviour), the container is ephemeral — data is lost
when the container stops.

### Why it matters
This is arguably the most impactful feature on the list. Right now, every database silently loses
all data if the container is restarted or if stop/start is used. Users working with real data (even
locally) need to know they can rely on persistence. It also teaches a real infrastructure concept —
the separation between compute (the container) and storage (the volume).

### How it works
The Docker Terraform provider has a `volumes` block on `docker_container` and a separate
`docker_volume` resource. When persistence is enabled, a named volume is created and attached
at the engine's data directory.

**Terraform change (example for PostgreSQL):**
```hcl
# New resource — only added when persistent = true
resource "docker_volume" "db_data" {
  name = "<db-name>-data"
}

resource "docker_container" "database" {
  name  = "<db-name>"
  image = "postgres:15"
  ...

  # Only present when persistent = true
  volumes {
    volume_name    = docker_volume.db_data.name
    container_path = "/var/lib/postgresql/data"
  }
}
```

**Data directory paths per engine:**
| Engine     | Container data path                  |
|------------|--------------------------------------|
| PostgreSQL | `/var/lib/postgresql/data`           |
| MySQL      | `/var/lib/mysql`                     |
| MariaDB    | `/var/lib/mysql`                     |
| MongoDB    | `/data/db`                           |
| Redis      | `/data`                              |

### Destroy behaviour
When a persistent database is destroyed, the volume must also be destroyed via
`terraform destroy`. The Terraform config with the `docker_volume` resource handles this
automatically — no extra logic needed in the backend.

### Changes required
- **Database schema** — add `persistent BOOLEAN NOT NULL DEFAULT false` column to `databases` table
- **`CreateDataBaseRequestDto`** — add optional `persistent` boolean field (defaults to `false`)
- **`DatabaseConfigProvider`** — conditionally add `docker_volume` resource and `volumes` block
  when `persistent = true`
- **`TerraformService.provisionDatabase`** — pass `persistent` flag through to config provider
- **`DatabaseProvisionService`** — read flag from request, pass to terraform
- **`DatabaseResponseDto`** — include `persistent` so the UI can show a "Persistent" badge
- **Frontend `DatabaseForm`** — add a toggle/checkbox for "Enable persistence"
- **Frontend `DatabaseTable`/`DatabaseDetailsModal`** — show a persistence indicator on each row

## Feature 3 — Memory Limit

### What it is
Allow the user to set an upper bound on how much RAM the database container can consume.
Presented as a simple size selection (S / M / L / XL) rather than a raw number, mapping to
specific megabyte values under the hood.

### Why it matters
On a local machine running multiple services, an unconstrained database can consume all available
memory. Offering size tiers mirrors how real cloud databases work (instance type / node size) and
gives users the mental model that infrastructure has a cost/capacity. It also prevents a single
provisioned instance from starving other containers on the machine.

### How it works
The Docker Terraform provider exposes a `memory` attribute on `docker_container` (value in MB).
The user picks a named tier and the backend maps it to the numeric value before writing the
terraform config.

**Tier mapping:**
| Tier  | Label       | Memory (MB) |
|-------|-------------|-------------|
| XS    | Micro       | 128         |
| S     | Small       | 256         |
| M     | Medium      | 512         |
| L     | Large       | 1024        |
| XL    | X-Large     | 2048        |

**Terraform change:**
```hcl
resource "docker_container" "database" {
  name   = "<db-name>"
  image  = "postgres:15"
  memory = 512   # templated from the selected tier
  ...
}
```

### Notes
- `memory = 0` in Docker means no limit — so omitting the field or setting it to 0 keeps the
  current unconstrained behaviour. The backend should treat a null/missing tier as "no limit".
- The frontend should make the default selection clear (e.g. "Medium — 512 MB (recommended)").

### Changes required
- **Database schema** — add `memory_mb INTEGER` column (nullable — null means no limit)
- **`CreateDataBaseRequestDto`** — add optional `memoryMb` integer field (or a `sizeTier` enum
  that the backend resolves to an integer)
- **`DatabaseConfigProvider`** — add `memory = <value>` to the container resource when
  `memoryMb` is non-null and non-zero
- **`TerraformService.provisionDatabase`** — pass `memoryMb` through to config provider
- **`DatabaseProvisionService`** — read field from request, pass to terraform
- **`DatabaseResponseDto`** — include `memoryMb` in the response
- **Frontend `DatabaseForm`** — add a size tier selector (radio group or dropdown)
- **Frontend `DatabaseTable`** — optionally surface the tier as a small label on each row

---

## Implementation Order

Suggested sequence for lowest-risk, highest-value delivery:

1. **Feature 2 — Persistence** (biggest real-world impact, teaches a key infra concept)
2. **Feature 1 — Version Picker** (visible, feels polished, very low backend risk)
3. **Feature 3 — Memory Limit** (quality-of-life, good finishing touch)
